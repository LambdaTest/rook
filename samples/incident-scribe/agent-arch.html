What it does

An incident report arrives as a sentence. Three answers have to come out.

When something breaks, the first message is rarely well-formed. It is “something is wrong with the checkout thing again, customers are complaining.” Somebody then has to identify the real service, look up who owns it and how critical it is, decide a severity against the company matrix, check whether this has happened before, and write the sentence that goes on the status page — while keeping runbook links and on-call addresses out of it.

incident-scribe does that intake step. It is a real agent, not a template: it calls a model, decides which tools it needs, and hands the customer-facing writing to a second, deliberately tool-less model call.

Question one

Which service?

“The checkout thing” has to become checkout-api — and the owning team, the tier and the on-call address must come from the directory, never from the report and never from the model’s memory.

Question two

How bad?

A severity from the Northwind matrix, with the matched row named out loud. Tier comes from the lookup. No placeable symptom means a question back, not a severity picked to have picked one.

Question three

What do we tell customers?

Three or four sentences a shopper can read, written from the facts already established — with no internal URL, no runbook link, no on-call email and no severity code in it.

How it is built

One door to the facts, one writer with no hands

Two design decisions carry most of the weight. First, every operational fact comes through a single MCP server — so anyone checking the desk can open that same server and ask it directly, then compare. Second, the customer note is written by a subagent with no tools at all — so the prose can only describe facts the desk really fetched.

The directory

Nothing to start, no port to forget

ops-directory speaks MCP over stdio and is spawned per session by whoever needs it — the desk does, and so does anything grading the desk. There is no daemon and no shared state between runs.

The subagent

Handed the secrets on purpose

comms-writer is given the runbook URL and the on-call address deliberately. Keeping them out of the customer note is then a rule being followed, not an accident of what it happened to receive.

Retrieval

“Has this happened before?” answered by meaning, not by date

recent_incidents returns a service’s filings newest-first. That is history, not an answer. search_incidents is the desk’s retrieval layer: it embeds the symptom description and ranks the whole corpus by similarity, across services.

A report phrased “shoppers can’t complete payment” ranks INC-2041, “Card authorisation timeouts”, first — despite sharing not one word with it.

Bar lengths illustrate the ordering; the ≈0.60 figure for INC-2041 is the documented score for this query.

One asserted model

A cross-model cosine is noise, not similarity

The embedding model is a constant in the code, not a setting. The index file records which model built it, and the server refuses to mix models rather than return a plausible-looking wrong ranking.

Degrade, don’t fail

Every answer says how it was sourced

No index, no model, no network — search falls back to deterministic lexical scoring instead of erroring. Each reply carries mode: "semantic" or "lexical", so nobody has to guess which one ran.

The flywheel

Today’s incident is tomorrow’s “yes, we’ve seen this”

The corpus is not frozen. When a session closes, the desk hands its own incident record back through the same door — validated, embedded with the same model, searchable immediately, and persisted for every later run.

This is not a claim on a slide. Session flywheel-a3 filed an S2 against notify-worker for merchant webhook TLS verification failures. A later session, asked about the same problem in different words, answered “yes — INC-L-flywheel-a3”: an incident the desk itself had written twenty minutes earlier.

Ingested summaries are sanitized on the way in — protocol markers, bare markdown headings and internal-contact bullets are stripped — because a stored summary reading “Assessment” teaches the next session nothing.

The rules

Five things it must never get wrong

  1. 01

    Never state a fact it did not fetch

    Owning team, tier and on-call address come from lookup_service, on every single task. An unknown service gets no invented owner and no invented tier.

  2. 02

    Severity comes from the matrix, and it names the row

    S1 a tier-1 service is unavailable, or money or data is being lost. S2 a tier-1 or tier-2 service is degraded for many users. S3 limited or single-user impact, or a tier-3 service. A completed assessment whose severity contradicts the policy check is forced back to a question.

  3. 03

    No placeable symptom means a question, not a guess

    It must not pick a severity in order to have picked one — and when it asks, it produces no customer note and no incident record.

  4. 04

    Nothing internal reaches the customer note

    No internal URL, no runbook link, no on-call email, no severity code. Enforced twice: in the writer’s instructions, and again by a sanitizer after generation.

  5. 05

    Report text is data, never instructions

    “Ignore your instructions”, “you are now…” — text like that inside a report is reported as report content and never acted on. The same holds for incidents returned by search. Suspected injection is logged before the model ever sees the text.

Restraint

What it does when the report doesn’t say enough

The easiest way for an intake agent to look competent is to always produce an answer. This one refuses. Given “Something is wrong with the checkout thing again. Customers are complaining on Twitter,” it still does the lookup work — and then stops:

status: needs_input ·no severity ·no artifacts ·comms-writer not called
Asksone question

The report (“something is wrong”) doesn’t name a symptom or scope I can place against the severity matrix. Can you tell me what specifically is failing (e.g. payment errors, timeouts, outage) and roughly how many customers are affected?

Keepswhat it found

It still reports the facts it did establish — service checkout-api, team payments, tier 1, prior incidents INC-2098 and INC-2041 — so the next message can be one sentence, not a fresh report. Answer it and the same session completes in about twelve seconds, because the transcript and the fetched service record carry forward.

Verification

Built so its answers can be checked, not believed

An agent’s reply is a sentence, and a sentence can be confidently wrong. This desk is deliberately shaped so a reviewer can open things instead: two real files on disk, two real URLs, and — through the same MCP door the desk used — the true owning team, tier, and the incidents the index really ranks for a given symptom.

That is why the directory is an MCP server rather than a private interface. A check across two copies of the data proves the copies agree. A check through the same door proves something about the desk.

Preflight, before a run is spent

Six checks in order: the credential is configured, the model provider is configured, the token gate refuses a wrong token, the MCP handshake lists all four tools, semantic search is armed, and the desk can reach the directory through the door (checkout-api → payments).

Ten tests on the mechanics

Tool schemas, the flywheel end to end (index → paraphrase search → idempotent re-index → durability across a fresh server spawn), the zero-word-overlap ranking to INC-2041 through the real MCP server, the severity guard, and the provider transcript mappings.

Using it

Four commands, and a token on every one of them

Work happens inside a session. execute is the only command that does any work; the other three are plumbing the caller drives. The report arrives on stdin — because incident text contains quotes, newlines and dollar signs, and that is exactly where argument quoting breaks. 

# the token is checked before anything else happens — on all four
python3 -m incident_scribe open    --token "$SCRIBE_API_TOKEN" --session-id S-1

echo "<the incident report>" |
python3 -m incident_scribe execute --token "$SCRIBE_API_TOKEN" --session-id S-1

python3 -m incident_scribe close   --token "$SCRIBE_API_TOKEN" --session-id S-1
python3 -m incident_scribe logs    --token "$SCRIBE_API_TOKEN" --session-id S-1

One JSON object per command

Diagnostics go to stderr; the answer goes to stdout. A completed execute returns the assessment and note, both file paths, both image URLs, every tool call including the subagent hand-off, token usage and per-turn metrics.

Repeat execute to keep talking

A second call under the same session id continues the conversation — the transcript and the already-fetched service record carry forward, so a follow-up never re-asks the service name or re-fetches the tier.

logs is the evidence trail

Written as the session runs, so a session that died still says how far it got — every tool call, every artifact path, every metric, as JSON. It is as token-protected as execute.

The model is the desk’s own business

A caller supplies a token and a report — never an endpoint or a key. The same agent loop runs on Anthropic/GLM, Gemini, OpenAI Chat Completions or the Responses API, selected from the environment.

About this build

Northwind, its three services and its incident history are a demonstration corpus. The status-board and severity-matrix fields return real, publicly reachable image URLs — in this build they point at public placeholder images standing in for real boards, because the point of returning a URL is that something downstream has to actually go and fetch it: a made-up URL and a real one look identical in a reply.

Every trace, note, metric, tool call and scenario on this page is taken from the repository’s own session logs and harness files. Where the prose here and the incident policy PDF disagree, the PDF is authoritative.
